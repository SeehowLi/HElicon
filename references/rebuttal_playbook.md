# Rebuttal Playbook

Run `H-REVIEW` with `review_gate.md` before drafting a rebuttal. The review provides the claim and evidence state that constrains every response.

## Triage classes

| Class | Diagnosis | Response skeleton |
|---|---|---|
| Factual error | The review relies on a verifiably incorrect premise | Thank the reviewer; state the correction narrowly; cite the exact manuscript or external evidence; explain whether clarification will be added. |
| Misreading | The manuscript contains the answer but made it hard to find | Acknowledge the ambiguity; answer directly; point to the current location; promise a precise clarification rather than blaming the reviewer. |
| Fixable real defect | The concern is valid and can be resolved within rebuttal or camera-ready limits | Concede the bounded issue; provide verified analysis or a feasible textual change; state how the claim will be scoped. |
| Unfixable real defect | The concern is valid but needs work beyond the response window | Concede the limitation; narrow the claim; state what will not be asserted; avoid speculative promises. |

## Tone rules

- Lead with the answer, not appreciation boilerplate.
- Be specific and non-adversarial. Correct the premise without characterizing the reviewer.
- Separate what the current manuscript already establishes from what will change.
- Preserve uncertainty and threat-model scope; rebuttal pressure does not license stronger language.
- Use the reviewer's identifier and concern consistently so responses remain traceable.

## Hard constraints

Do not introduce a new experimental number unless it has been independently verified and recorded in the evidence map. Do not imply that a planned run has already completed.

Every promised revision must be feasible within the camera-ready deadline. If feasibility is uncertain, narrow the promise to a clarification, limitation statement, or claim adjustment that can be delivered.

## Output check

For each response record the triage class, direct answer, evidence pointer, promised manuscript change, owner or dependency, and feasibility status. Finish with unresolved risks rather than concealing them.
